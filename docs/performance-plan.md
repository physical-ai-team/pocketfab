# PocketFab 성능 측정 계획

담당: 김세광. 측정 결과는 이 문서 하단의 결과표에 누적 기록한다.

## 1. 측정 환경

| 항목 | 개발 PC 기준 |
|---|---|
| CPU | AMD Ryzen 7 5700U (8코어 / 16스레드) |
| GPU | 없음 (AMD 내장 그래픽, CUDA 불가) → **CPU 추론** |
| RAM | 약 14GB |
| 실행 | Windows 11 + Docker Desktop (WSL2 백엔드) |

**Docker Desktop의 자원 한도에 주의한다.** 컨테이너는 WSL2 가상머신 안에서 돌기 때문에
`%UserProfile%\.wslconfig`의 `processors`, `memory` 설정이 실제 상한이 된다.
측정 전에 이 값을 기록하고, 측정 중에는 다른 무거운 프로그램을 끈다.

```ini
# %UserProfile%\.wslconfig 예시
[wsl2]
processors=8
memory=10GB
```

## 2. CPU 환경에서 Scale-out이 제한적인 이유

GPU 서버에서는 C3 복제본마다 별도의 연산 자원(GPU)을 붙일 수 있지만, 이 PC에서는
**모든 C3 복제본이 같은 8개 물리 코어를 나눠 쓴다.** 그래서 다음과 같은 현상이 예상된다.

1. **총 연산량의 상한은 고정이다.** 복제본을 늘려도 CPU가 이미 100%라면 처리량(fps)은 늘지 않는다.
2. **스레드 과다 할당(oversubscription)이 성능을 떨어뜨린다.** PyTorch는 기본적으로 코어 수만큼
   스레드를 쓴다. 복제본 4개가 각각 8~16개 스레드를 쓰면 문맥 전환과 캐시 경합 때문에
   **복제본 1개일 때보다 오히려 느려질 수 있다.**
3. **그래도 이득이 있을 수 있는 부분이 있다.** PyTorch의 연산 내부 병렬화(intra-op)는 스레드 수에 비례해
   빨라지지 않는다. 그래서 "1개 × 8스레드"보다 "2개 × 4스레드"의 총 처리량이 약간 더 높을 수 있다.
   또 JPEG 디코딩, 후처리, 네트워크 대기처럼 추론이 아닌 구간이 겹치면서 생기는 이득도 있다.
   대신 프레임 1장의 지연시간은 늘어난다.
4. **메모리도 상한이다.** 복제본마다 SAM 2 모델을 따로 올리므로 RAM 사용량이 복제본 수에 비례한다.

따라서 이 프로젝트에서 Scale-out의 목표는 "복제본을 늘리면 선형으로 빨라진다"를 보이는 것이 **아니다.**
**아키텍처가 수평 확장을 지원한다는 점과, CPU 환경에서 어디서 포화되는지를 수치로 보이는 것**이다.
GPU 또는 다중 노드 환경으로 옮기면 같은 구성으로 선형에 가까운 확장이 가능하다는 점을 근거로 제시한다.

### 운영 규칙
- `C3 복제본 수 × TORCH_NUM_THREADS ≤ 물리 코어 수(8)`로 맞춘다.
- C3 컨테이너에 `OMP_NUM_THREADS`, `MKL_NUM_THREADS`를 `TORCH_NUM_THREADS`와 같게 설정한다.
- 필요하면 compose의 `cpus:` 제한으로 복제본 간 공정성을 확보한다.

| E7. `IN_FLIGHT_PER_REPLICA` | 1, 2, 4 (`MAX_IN_FLIGHT`는 비워 자동 계산) | 지연시간·처리량·C2 낭비 사이의 득실 확인. 예비 실험(추론 200ms 흉내, 복제본 2): 1 → 8.0fps, 2 → 8.9fps |

## 5. 측정 방법

1. **재현성을 위해 스마트폰 대신 녹화 영상을 쓴다** (README "입력 방식" ②). 시뮬레이터 화면 녹화(`data/videos/*_screen.mp4`)를 30fps로
   `python tools/fake_camera.py --video ...`로 `/ws/camera`에 보낸다.
   폰 실측(③)은 최종 구성에서만 별도로 1회 기록한다. 폰 영상은 화질이 들쭉날쭉해서 구성 간 비교에는 쓰지 않는다.
2. 구성마다 워밍업 10초를 버린 뒤 60초를 측정하고, 3회 반복해 중앙값을 기록한다.
3. 실행 예시 (E3, 2×4):
   ```powershell
   $env:TORCH_NUM_THREADS = "4"
   docker compose up -d --scale c3-inference=2
   ```
4. 측정할 때마다 `.wslconfig` 값, 커밋 해시, 환경변수를 결과표에 함께 기록한다.

## 7. 정확도 평가 계획 (시뮬레이터 정답 라벨)

처리 속도(1~6장)와 별개로, **마스크가 얼마나 정확한지(IoU)** 와 **판정 임계값을 어디에 둘지**를 시뮬레이터의 정답 라벨로 측정한다.

### 7.1 정답 라벨 JSON 분석 (`labels_*.json`)

시뮬레이터 `exportLabels()`가 만드는 형식이다.

| 필드 | 내용 | 평가에서의 쓰임·주의 |
|---|---|---|
| `image.width`, `image.height` | 캔버스 픽셀 크기 = 저장된 PNG 크기 | **PNG 크기와 다르면 짝이 틀린 것**이므로 그 쌍을 버린다 |
| `image.dpr` | 디스플레이 배율 (최대 2) | 좌표는 이미 배율이 곱해져 있으므로 따로 처리할 필요 없음 |
| `params` | 저장 시점의 모든 슬라이더 값 + `scan_line_x`(검사선의 픽셀 x) | 결손 크기·조명·노이즈별로 결과를 나눠 볼 때 쓴다 |
| `counts.total_passed`, `defect_passed` | 리셋 이후 검사선을 통과한 누적 개수 | 집계 방식 검증에 쓸 수 있다 (영상 단위) |
| `annotations[].category` | `round`(정상) / `deformed`(불량 4종 모두) | 이진 판정의 정답 |
| `annotations[].defect_type` | `bite` / `cut` / `wedge` / `half` / `null` | 유형별 재현율 |
| `annotations[].bbox` | `[x, y, w, h]` 픽셀 (COCO 방식, 좌상단 + 크기) | 우리 스펙은 `[x1, y1, x2, y2]` 0~1이므로 변환해서 비교 |
| `annotations[].segmentation` | `[[x1, y1, x2, y2, ...]]` 180점 폴리곤, 픽셀 (COCO 방식) | `cv2.fillPoly`로 정답 마스크 생성 |
| `annotations[].roundness` | 반경 최솟값 / 최댓값 (시뮬레이터 자체 지표) | 우리 원형도와는 다른 값. 결손 정도 참고용 |
| `annotations[].diameter_px` | 결손 전 원의 지름 (모든 과자 동일) | 기준 면적 `π(d/2)²` 계산에 쓸 수 있다 |

형식에서 주의할 점
- **화면 밖으로 일부 나간 과자도 라벨에 들어 있다.** 이런 과자는 폴리곤 좌표가 0보다 작거나 이미지 폭보다 크다.
  bbox가 이미지 경계에 닿으면 **`truncated`로 표시하고 지표 계산에서 뺀다.** 예측 쪽도 같은 기준으로 뺀다.
- 정답 폴리곤은 그림자를 포함하지 않는다. 그림자를 마스크에 포함하는 세그멘터는 IoU가 낮게 나온다.
- 정상 과자도 `segmentation`은 180점 폴리곤이다. 원으로 그려도 형식은 같다.

### 7.2 평가 스크립트 계획 (`tools/eval/evaluate.py`, 작성 예정)

```powershell
python tools/eval/evaluate.py --data data/sim/20261103_mix-d78-s55-l20-n0 --segmenter opencv
```

1. **쌍 불러오기**: `NNNN.png` + `NNNN.json`. 이미지 크기가 맞지 않는 쌍은 경고하고 건너뛴다.
2. **정답 준비**: 폴리곤 → 마스크. 정답 마스크에서도 원형도·solidity를 계산한다(래스터화된 정답이 낼 수 있는 최선의 값). `truncated`를 표시한다.
3. **예측**: C2의 `preprocess()`·`detect_boxes()`와 C3의 세그멘터·`judge`를 실행한다.
   **파이프라인(HTTP)은 거치지 않고 함수를 직접 호출한다** (README "입력 방식" ①).
   C1의 백프레셔 때문에 프레임과 라벨의 짝이 끊기고, 대시보드 결과에는 윤곽선이 없기 때문이다.
   이미지는 C2와 같은 `PREPROC_WIDTH`로 리사이즈한 뒤 넣고, 비교는 정규화 좌표(0~1)로 한다.
4. **매칭**: 정답과 예측 마스크 사이의 IoU 행렬을 만들고, 헝가리안 매칭 후 IoU ≥ 0.5인 쌍만 인정한다.
5. **지표**

| 구분 | 지표 | 무엇을 보나 |
|---|---|---|
| 검출 (C2) | 박스 재현율·정밀도 | 과자를 빠짐없이 찾는지, 벨트·그림자를 과자로 착각하지 않는지 |
| 마스크 (C3) | IoU 평균·중앙값·하위 5% (유형별, 결손 크기·조명·노이즈별) | SAM 2와 opencv 모드의 마스크 품질 비교 |
| 지표 오차 | 예측 마스크와 정답 마스크의 원형도·solidity 차이 | 마스크 오차가 판정에 얼마나 번지는지 |
| 판정 | 혼동행렬(정상/불량), 유형별 재현율, **정상 오경보율** | 최종 성능 |

6. **임계값 보정**: 보정용(calib) 세션에서 **예측 마스크의 지표**와 정답 `category`를 모은다.
   (원형도, solidity, 원 채움률) 세 임계값 조합을 격자 탐색해서 OR 규칙의 성능을 계산하고, **정상 오경보율 ≤ 2%를 지키면서 불량 재현율이 가장 높은 조합**을 고른다.
   고른 값은 검증용(test) 세션에서 다시 확인한 뒤 `.env.example`과 api-spec 6장의 기본값에 반영한다.
   예측 마스크로 보정하는 이유는 실제 실행에서 쓰는 마스크가 정답 마스크가 아니라 예측 마스크이기 때문이다.
7. **출력**: `results/eval/<날짜>_<세션>/` (git 제외)
   - `objects.csv`: 객체 1개당 1행 (정답 유형, IoU, 지표, 판정)
   - `summary.json`: 위 지표 요약
   - 유형별 원형도·solidity 히스토그램 PNG
