# PocketFab 측정 계획

담당: 김세광.

최종 확인은 **줌 온라인 수업에서의 실시간 시연**이다 (README "줌 시연 방법"). 그래서 측정은 시연에 꼭 필요한 것만 **필수**로 하고,
나머지는 **선택(시간이 남으면)** 으로 둔다. 영상을 많이 모으거나 조건별로 나눠 수집하는 계획은 하지 않는다.

## 1. 범위

| 항목 | 구분 | 데이터 | 도구 | 예상 시간 |
|---|---|---|---|---|
| ① 평가 데이터 만들기 | **필수** | 자동 캡처 세션 2개 (보정용 1, 확인용 1) | 시뮬레이터 "자동 캡처" | 10분 |
| ② 임계값 보정 | **필수** | 보정용(calib) 세션 | `tools/c3_eval.py` | 30분 |
| ③ 정확도 확인 | **필수** | 확인용(test) 세션 | `tools/c3_eval.py` | 10분 |
| ④ 예비 녹화 영상 | 선택 (시간이 남으면) | 1~2분 영상 1~2개 | OBS 등 화면 녹화 | 10분 |
| ⑤ Scale-out 전후 비교 | 선택 (시간이 남으면) | ④의 영상 | `tools/fake_camera.py --video` | 20분 |

선택 항목을 하지 않았을 때의 영향
- ④가 없으면 줌 시연 중 폰 연결이 끊겼을 때 대신 보여줄 영상이 없다. 그때는 `python tools/fake_camera.py`(합성 영상)로 파이프라인이 동작하는 것만 보여준다.
- ⑤가 없으면 Scale-out 효과를 숫자로 보여줄 수 없다. 대신 시연 중 대시보드의 "처리 현황 → C3 복제본별 fps"로 **요청이 여러 복제본에 나뉘는 모습**은 보여줄 수 있다.

## 2. 필수 ① 평가 데이터 만들기

시뮬레이터의 **자동 캡처**로 만든다 (README "시뮬레이터 사용법"). 사람마다 직접 만들어 쓰고, 공유 저장소는 쓰지 않는다 (README "평가 데이터").

| 세션 | 용도 | 권장 설정 |
|---|---|---|
| `calib` | 임계값 보정 (②) | 시연과 같은 설정, 혼합 랜덤, 불량률 30~50%, 30쌍, 간격 30프레임 |
| `test` | 정확도 확인 (③) | `calib`과 같은 설정으로 **따로 한 번 더** 캡처 (라인 비우기 후 다시 시작) |

- **두 세션을 반드시 나눈다.** 같은 데이터로 보정하고 확인하면 정확도가 실제보다 좋게 나온다.
- 설정은 **시연 때 쓸 설정**(지름, 결손 크기, 조명)에 맞춘다. 시연과 다른 조건을 따로 모으지 않는다.
- 간격을 30프레임(1초) 이상으로 잡으면 같은 과자가 여러 쌍에 반복되는 일이 줄어든다.

## 3. 필수 ② 임계값 보정

`tools/c3_eval.py`는 정답 bbox를 C2 박스 대신 넣고 C3 판정만 채점한다. 임계값은 C3와 같은 환경변수를 읽으므로,
값을 바꿔 가며 보정용 세션으로 돌린다.

```powershell
conda activate pocketfab
python tools/c3_eval.py data/sim/calib                       # opencv 모드, 현재 기본 임계값
python tools/c3_eval.py data/sim/calib --masks gt            # 정답 폴리곤: 판정 규칙의 한계 확인
python tools/c3_eval.py data/sim/calib --segmenter sam2      # 시연에서 쓸 마스크 (로컬에 SAM 2 설치, checkpoints/ 필요)
```

1. **시연에서 쓸 세그멘터**(`sam2`)로 채점한다. 실제로 판정에 쓰이는 마스크가 정답 마스크가 아니라 예측 마스크이기 때문이다.
2. 출력의 `정상 오경보`와 `놓친 불량`을 보고, 해당 지표의 임계값만 조금씩 옮긴다.
   ```powershell
   $env:CONCAVITY_THRESHOLD = "0.05"; python tools/c3_eval.py data/sim/calib --segmenter sam2
   ```
3. 기준: **정상 오경보율 2% 이하**를 지키면서 불량 Recall이 가장 높은 값을 고른다.
4. 정한 값을 `.env`에 적는다. 기본값과 달라졌으면 `.env.example`과 api-spec 6장도 같은 PR에서 고친다.

측정 조건 (박민성, 2026-10-28)
- 데이터: 자동 캡처 `calib`·`test` 각 30쌍 (간격 30프레임), 시뮬레이터 기본값(라인 3, 지름 78px, 결손 55%, 조명 20, 노이즈 0)에 **불량률 40%**. 화면 끝 과자를 뺀 객체 405개씩.
- 보정(②): `calib`에서 SAM 2 마스크 지표로 네 임계값을 격자 탐색한 결과 **기본값이 그대로 최적**이었다 (Recall 1.000, 오경보 0%). 그래서 임계값은 바꾸지 않았다.
  `calib`에서 정상/불량 사이 여유: 원 채움률 정상 최소 0.959 vs 불량 최대 0.934, 오목 깊이 정상 최대 0.032 (임계값 0.06).
- SAM 2 지연 p50 약 3.3초/프레임 (CPU, `TORCH_NUM_THREADS=4`, 우선순위 낮춤).
- opencv 기준선도 불량 여부는 다 맞히지만 유형을 자주 틀린다 (`half`→`bite` 17/21, `cut`→`bite` 7/38). SAM 2는 유형까지 모두 맞혔다.

시연 해상도 확인 → `FILL_RATIO_THRESHOLD` 0.94 → 0.93 (박민성, 2026-10-28)
- 시연은 폰이 640×480으로 모니터를 찍고 C2가 가로 640px로 맞추므로, 과자 지름이 78px보다 작아진다 (컨베이어가 폰 화면을 꽉 채워도 약 49px).
- `calib` 프레임을 줄여서 SAM 2로 다시 쟀다 (정답 폴리곤·박스도 같은 비율로 변환, 객체 405개).

| 조건 | 과자 지름 | 정상 원 채움률 최소 | Recall | 정상 오경보 (0.94) | 정상 오경보 (0.93) | 유형 정확도 | IoU |
|---|---|---|---|---|---|---|---|
| 원본 | 78px | 0.959 | 1.000 | 0/229 | 0/229 | 1.000 | 0.973 |
| 0.63배 (폰 화면을 꽉 채움) | 약 49px | 0.948 | 1.000 | 0/229 | 0/229 | 0.994 | 0.969 |
| 0.5배 (조금 멀리서) | 약 39px | **0.934** | 1.000 | **1/229** | 0/229 | 1.000 | 0.958 |

- 0.93에서도 세 조건 모두 놓친 불량이 없다 (`cut`의 원 채움률은 최대 0.876).
- 흐림·JPEG 압축·원근 왜곡 조건은 메모리 부족으로 측정하지 못했다. 시연 리허설에서 확인한다.

작은 불량 포함 확인 (김세광, 2026-10-28) — 표의 "결손 25% 포함" 줄
- 위 데이터는 결손 55%뿐이라, 원 채움률 0.93에서 작은 `cut`을 놓치지 않는지 따로 확인했다.
  결손 크기는 슬라이더 하나로 모든 불량에 적용되므로 세션마다 결손 55% 15쌍 + 결손 25% 15쌍을 나눠 캡처했다
  (나머지 설정은 위와 같고 간격 90프레임, 이미지 1314×450, 원본 해상도로 채점).
- 0.93에서 `calib`·`test` 모두 Recall 1.000, 정상 오경보 0%다. 결손 25% `cut`도 모두 잡았다.
  0.94에서는 `test`에 정상 오경보가 1건(1/315) 있었고 0.93에서 사라졌다.
- SAM 2가 틀린 것은 유형 1건(`half`→`bite`)뿐이다. opencv는 `half`→`bite` 38개, `cut`→`bite` 4개로 유형을 틀린다.
- SAM 2 지연 p50 약 4.4초/프레임 (과자 약 18개, `TORCH_NUM_THREADS=8`). 로컬 conda에 torch가 없으면 C3 컨테이너 안에서 채점할 수 있다:
  ```powershell
  $r = (Get-Location).Path
  docker compose run --rm --no-deps -v "${r}\tools:/srv/tools" -v "${r}\data:/srv/data" -v "${r}\c3-inference:/srv/c3-inference" `
    -e TORCH_NUM_THREADS=8 -e OMP_NUM_THREADS=8 c3-inference python tools/c3_eval.py data/sim/test --segmenter sam2
  ```

참고: 박민성이 시뮬레이터 4조건에서 먼저 잰 결과(SAM 2 tiny, 4지표 기준)는 Recall 1.000, 유형 정확도 1.000, IoU 0.97이다 (api-spec 7.3).

## 5. 선택 ④ 예비 녹화 영상 (시간이 남으면)

**용도는 두 가지뿐이다.** 줌 시연 중 폰 연결이 불안정할 때 대신 보여주는 예비용, 그리고 ⑤ Scale-out 비교 입력.

- 시연 설정 그대로 시뮬레이터 컨베이어 영역만 **1~2분** 화면 녹화한다 (OBS 등, 30fps). 1~2개면 충분하다.
- 저장: `data/videos/demo.mp4` (git 제외).
- 녹화를 끝낼 때 시뮬레이터 카운터(검사 통과 / 불량)를 메모해 두면 대시보드 "누적 집계"와 비교할 수 있다.
- 재생: `python tools/fake_camera.py --video data/videos/demo.mp4 --seconds 120` (README "줌 시연 방법"의 예비 전환).

## 6. 선택 ⑤ Scale-out 전후 비교 (시간이 남으면)

④의 영상을 같은 조건으로 넣고 C3 복제본 수만 바꿔서 **한 번씩만** 잰다.

```powershell
$env:SEGMENTER = "sam2"; $env:TORCH_NUM_THREADS = "8"
docker compose up -d --build --scale c3-inference=1
python tools/fake_camera.py --video data/videos/demo.mp4 --seconds 60     # 처음 10초는 워밍업으로 보고 무시

$env:TORCH_NUM_THREADS = "4"
docker compose up -d --scale c3-inference=2
python tools/fake_camera.py --video data/videos/demo.mp4 --seconds 60
```

각 실행이 끝나면 `https://localhost/v1/metrics`와 대시보드의 처리 fps를 아래 표에 적는다.

| 날짜 | 복제본 × 스레드 | 세그멘터 | 처리 fps | 드롭률 | 복제본별 처리 수 | 비고 |
|---|---|---|---|---|---|---|
| | 1 × 8 | sam2 | | | | |
| | 2 × 4 | sam2 | | | | |

### CPU 환경에서 Scale-out이 제한적인 이유 (결과 해석용)

개발 PC(Ryzen 7 5700U, 8코어, GPU 없음)에서는 **모든 C3 복제본이 같은 8개 코어를 나눠 쓴다.**
- 총 연산량의 상한이 고정이라, 복제본을 늘려도 CPU가 이미 100%면 처리량은 거의 늘지 않는다.
- PyTorch는 기본적으로 코어 수만큼 스레드를 쓴다. 그래서 `복제본 수 × TORCH_NUM_THREADS ≤ 8`로 맞춰야 한다.
  넘기면 오히려 느려질 수 있다 (compose가 `OMP_NUM_THREADS`, `MKL_NUM_THREADS`도 같은 값으로 맞춘다).
- 복제본마다 SAM 2 모델을 따로 올리므로 메모리도 복제본 수에 비례한다.
  Docker Desktop은 `%UserProfile%\.wslconfig`의 `processors`, `memory`가 상한이다.

따라서 목표는 "선형으로 빨라진다"가 아니라, **수평 확장 구조가 동작하고 CPU 한 대에서는 어디서 포화되는지**를 보이는 것이다.
GPU나 여러 대의 PC로 옮기면 같은 구성으로 확장된다는 점을 근거로 든다.

## 7. 참고: 정답 라벨 형식

### 7.1 정답 라벨 JSON 분석 (`labels_*.json`, 자동 캡처의 `NNNN.json`)

시뮬레이터 `buildLabels()`가 만드는 형식이다.

| 필드 | 내용 | 평가에서의 쓰임·주의 |
|---|---|---|
| `image.width`, `image.height` | 캔버스 픽셀 크기 = 저장된 PNG 크기 | **PNG 크기와 다르면 짝이 틀린 것**이므로 그 쌍을 버린다 |
| `image.dpr` | 디스플레이 배율 (최대 2) | 좌표는 이미 배율이 곱해져 있으므로 따로 처리할 필요 없음 |
| `params` | 저장 시점의 모든 슬라이더 값 + `scan_line_x`(검사선의 픽셀 x) | 어떤 설정으로 만든 데이터인지 확인할 때 쓴다 |
| `counts.total_passed`, `defect_passed` | 리셋 이후 검사선을 통과한 누적 개수 | 집계 결과와 비교할 때 참고 |
| `annotations[].category` | `round`(정상) / `deformed`(불량 4종 모두) | 이진 판정의 정답 |
| `annotations[].defect_type` | `bite` / `cut` / `wedge` / `half` / `null` | 유형별 재현율, `defect_type` 추정 정확도 |
| `annotations[].bbox` | `[x, y, w, h]` 픽셀 (COCO 방식, 좌상단 + 크기) | 우리 스펙은 `[x1, y1, x2, y2]` 0~1이므로 변환해서 비교 |
| `annotations[].segmentation` | `[[x1, y1, x2, y2, ...]]` 180점 폴리곤, 픽셀 (COCO 방식) | `cv2.fillPoly`로 정답 마스크 생성 |
| `annotations[].roundness` | 반경 최솟값 / 최댓값 (시뮬레이터 자체 지표) | 우리 원형도와는 다른 값. 결손 정도 참고용 |
| `annotations[].diameter_px` | 결손 전 원의 지름 (모든 과자 동일) | 기준 면적 `π(d/2)²` 계산에 쓸 수 있다 |
| `sequence` (자동 캡처만) | `index`(1부터), `count`, `step_frames`, `dt_s`(쌍 사이 시간) | 연속 쌍으로 추적·집계(C4)를 시험할 때 시각 정보로 쓴다. 같은 `annotations[].id`는 같은 과자다 |

형식에서 주의할 점
- **화면 밖으로 일부 나간 과자도 라벨에 들어 있다.** 이런 과자는 폴리곤 좌표가 0보다 작거나 이미지 폭보다 크다.
  bbox가 이미지 경계에 닿으면 지표 계산에서 뺀다 (`tools/c3_eval.py`의 `is_truncated`).
- 정답 폴리곤은 그림자를 포함하지 않는다. 그림자를 마스크에 포함하는 세그멘터는 IoU가 낮게 나온다.
- 정상 과자도 `segmentation`은 180점 폴리곤이다.
